# Identity and staff administration

Customers are independent company-owned identities in `company_customers`, uniquely identified by `(company_id, canonical phone)` with a UUID primary key. The same phone in different salons never joins identities, profiles, history, blocks or sessions. There is no `customer_accounts` table or global customer lookup. Staff credentials remain independent from customers even when contact phones match. See [ADR-0017](./adr/0017-company-local-customers.md).

Both OTP endpoints require `companyId` and an explicit international phone (`+` plus 9–15 digits, first digit nonzero). No country is inferred; syntax alone does not validate country allocation or unify legacy national forms. Requesting a code creates only a company-scoped delivery intent; successful verification atomically upserts a local customer with phone and no names. Codes belong to `(companyId, phone)` and cannot authenticate another salon. An absent company returns 404 before issuing/consuming a code. Phone cooldown/issuance limits and the daily SMS budget remain shared across salons.

The first successful customer or staff booking requires first/last name and sets `first_booking_at` atomically with the booking. Failed bookings leave the identity pending. Before this marker, the identity is invisible to staff customer lists, details, visits, notes, profile changes and block operations (opaque 404). Cancelling or archiving every visit never removes established visibility. Names, optional contact email and private notes are company-owned; only staff may edit established profiles. Phone is immutable through profile APIs. Profile list/detail includes `revision`; staff profile and notes PUT require `If-Match` and increments the same row version as first establishment. Pending rows are not proof of OTP verification: staff may establish them without OTP.

Both staff roles can list/read their company's established customers, notes, contact data and visit history. `/api/customers/{id}` and reservation `customerId` identify `company_customers.id`. Other-company and absent/invisible resources return the same 404. `/api/users/me` returns `{id,phoneNumber,companyId,profileState}` with advisory `PENDING|ESTABLISHED` readiness and no salon-owned names for the current local customer; `/api/auth/me` also returns that customer's `companyId`, with `employmentId:null`.

Staff accounts belong to one company. The compatibility endpoint `POST /api/auth/login-staff` requires `companyId`, `email`, and `password`; email is trimmed and lowercased inside that company's namespace. Phone is optional contact information and never participates in authentication. The same email or contact phone in another salon, or in the customer realm, grants no shared identity or access. Profiles, photos, role, enabled state, credentials, and qualification mode belong to `company_employees`. Public employee IDs are allocated independently from customer accounts.

Owners create EMPLOYEE accounts using `POST /api/employees`. The response contains the profile and a one-use initial password setup token for secure handoff. Owners edit names, login email, and optional contact phone with `PUT /api/employees/{id}`; photo upload/delete remain separate owner endpoints. Owner account provisioning and role changes are operator-controlled; these APIs cannot create an OWNER, change roles, or disable an owner.

`POST /api/employees/{id}/password-link` replaces the employee's initial setup/recovery token. Only its SHA-256 hash is stored. Tokens expire after exactly 24 elapsed hours, are single-use, and replacement or account disabling invalidates prior tokens. The owner receives the plaintext token once; it is never part of ordinary profile reads or logs. `POST /api/auth/staff-password` consumes the token and sets a password without logging the employee in. This anonymous browser write requires CSRF.

Authenticated staff use `POST /api/staff/password` with `currentPassword` and `newPassword`. Current-password verification does not authenticate or create a session. Password change/reset increments the durable account `auth_version` and revokes every session of that staff account after commit. Every request revalidates the version, so Redis cleanup failure cannot preserve old access. Staff login locks the credential row and captures the session generation before password validation; a validated login response saved after a reset remains invalid. Failed password changes preserve existing sessions.

`PUT /api/employees/{id}/enabled` changes access state. Disabling immediately invalidates sessions and setup/recovery links, removes customer booking eligibility, and returns affected future bookings without changing those appointments. Re-enabling cannot revive old links or sessions. Eligibility mutations lock company then employee, matching booking allocation lock order.

Employee photo bytes are decoded and validated before upload. Each company writes its own photo reference. Existing objects are deleted only after commit and only when no other staff profile still references them, including legacy shared photos. Rollback compensates a newly uploaded object. Cleanup failures may leave an unreferenced object for operator cleanup; they cannot leave a committed database reference pointing to a deliberately deleted object.


The consolidated pre-production V1 baseline creates only the independent current realms. It does not retain global customer or legacy users tables, or infer staff/customer identity relationships from matching phone/email.

## Email-first staff sign-in

`POST /api/auth/login-staff-email` accepts `{email,password}` with CSRF in an anonymous browser. Email is normalized with trim and Locale.ROOT lowercase. Passwords are checked separately against immutable, bounded company-owned credential snapshots with exactly five BCrypt comparisons outside transactions. Only matching accounts are reloaded under short pessimistic locks in deterministic account-ID order; exact identity, company, normalized email, hash, enabled state, role and auth_version must remain unchanged. Revocation generations are captured before credential reads and checked again after revalidation and before session establishment. One match returns a TOTP verification or mandatory enrollment challenge, without an authenticated session. Multiple matches return `{status:"COMPANY_SELECTION_REQUIRED",selectionToken,companies:[{companyId,name}]}` containing only verified companies, without an authenticated session. No matches, disabled/passwordless accounts and wrong passwords return the same 401 `INVALID_CREDENTIALS` detail. Customer OTP is unchanged.

`POST /api/auth/complete-staff-login` accepts `{selectionToken,companyId}` with CSRF, anonymously. The opaque 256-bit random token is held in browser memory only. Redis stores scalar verified account IDs, company/user/role/email, exact auth_version and captured session generation under a SHA-256 token lookup for 120 seconds, never plaintext passwords or password hashes. The grant also contains a SHA-256 binding to the originating anonymous server-side session ID. The browser must retain its HttpOnly SESSION cookie; CSRF refreshes do not rotate this anonymous session. Atomic GETDEL consumes the grant before any selection checks, including wrong-browser/wrong-company choices and database rollback. Expired/reused/mismatched grants return the generic 401. Selection reloads and locks the exact account and compares enabled state, role, identity, auth_version and original generation. Completion returns a TOTP verification/enrollment challenge instead of creating a staff session. Completion uses a separate IP allowance with the same configured limit/window (`rate:login:completion:<ip>`), counting invalid, expired and replayed requests too. Exhausting the password-verification IP allowance does not prevent completing an accepted verification. Only final successful TOTP verification/enrollment creates a session, after transaction commit through the existing fixation/CSRF strategies. Reset/disable or logout-all races cannot revive a prior grant or delayed session save.

Every email-first attempt consumes one IP and one normalized-email SHA-256 limiter allowance, regardless of candidate count. Completion consumes an IP allowance. Limits fail closed through Redis and return 429 with Retry-After. Discovery reads at most six IDs and performs exactly five BCrypt checks, including dummy padding, to bound CPU and reduce membership timing differences. **More than five company accounts for an email require company-scoped login**, even if fewer passwords match. The response remains the generic credentials error, never a count or company hint. A user can obtain their salon's company ID privately from its administrator and expand “Logowanie do wskazanej firmy” in the dashboard to use the existing `/api/auth/login-staff` contract; this verifies one account without truncating membership or weakening authorization. Normal dashboard login needs no company UUID. Operators should provide this fallback to high-membership users; do not raise the work cap without capacity review.

Deploy the backend and dashboard together: every staff login contract now requires TOTP completion. The authorized pre-production V1 baseline includes `(login_email,id)` lookup indexing; existing applied databases must be rebuilt under the baseline convention before deployment, never bypass Flyway checksum validation.

Explicit booking intent, phone audit and unresolved shared/recycled-phone limits are defined in [ADR-0018](./adr/0018-explicit-booking-customer-intent.md).

## Phone-key audit before enabling native booking

New OTP and staff-new input requires an explicit international number; existing keys are never rewritten during login or booking. On an existing development dataset, this read-only query lists keys that need review:

```sql
SELECT company_id, id, phone_number, first_booking_at
FROM company_customers
WHERE phone_number !~ '^\+[1-9][0-9]{8,14}$'
ORDER BY company_id, id;
```

For each flagged row, authorized salon staff must confirm the intended full number and inspect any existing same-company international row. Similar digit suffixes or matching names are only review hints, never proof that two accounts represent the same person. The uniqueness constraint protects exact keys; syntax does not establish equivalence, country allocation or current phone ownership. Keep this report private and do not export customer phones to logs or public endpoints.

There is no phone correction, merge or reassignment API in this change. If review finds an ambiguous national/international pair, shared phone, recycled number or mistaken staff number, resolve it with the salon before allowing a new native booking for that number. Any future corrective migration must explicitly preserve reservation/submission links, audit history and tenant scope, handle exact-key collisions, and revoke affected sessions. Do not automatically add `+48`, merge by name, delete identities or reset a database. A fresh isolated test dataset requires no legacy remediation.

## Customer read pages

GET /api/customers and /api/customers/{id}/visits retain array responses and accept page=0 and size=100 by default (size 1–200). The directory orders by last name, first name, ID; visits by start descending, ID descending. Each response includes X-Page-Context and, while more rows exist, X-Next-Page. Follow all pages for full-list search, reject context changes and discard cancelled reads. Directory block states and rolling-year active penalty counts by Warsaw date are loaded in batches for page IDs. Pending/foreign customers remain excluded. Staff visits retain internal notes; customer history does not expose them. See [ADR-0021](./adr/0021-bounded-customer-reads.md).

## Mandatory staff TOTP

Every company-owned OWNER and EMPLOYEE enrolls independently. Password verification and company selection return TOTP_REQUIRED or TOTP_SETUP_REQUIRED with a ten-minute browser-bound challengeToken/expiresAt and the verified companyId. The dashboard retains this company scope when recovering an uncertain response. Only totp/verify or totp/setup/confirm can return AUTHENTICATED and create a staff session. Old staff sessions without a version-bound MFA proof no longer authorize. Customer SMS login is unchanged. See [ADR-0022](./adr/0022-mandatory-staff-totp.md).

Enrollment returns a manual Base32 key and otpauth URI for a locally generated QR. Confirm a six-digit code before activation. Only an owner receives ten recovery codes, shown before confirmation and never exposed by a subsequent read endpoint. The dashboard requires acknowledgement that these were saved. Pending secrets and codes expire with the challenge; active secrets are encrypted, while recovery codes are hashed. TOTP Redis challenge payloads are encrypted; company-selection grants retain their existing scalar JSON snapshots without TOTP secrets. Successful proof allowance release is best-effort after SQL commit; cleanup failure retains the allowance until expiry without changing the committed operation result. Codes use SHA1/6 digits/30 seconds with ±1-step tolerance and strictly increasing accepted counters, including during owner reauthentication for reset.

Owner recovery requires password plus a one-use recovery code and then a new TOTP enrollment. The previous secret remains active until confirmation. Code consumption and a durable authorization for the original challenge commit together. Recovery returns the same challenge token; after a lost response, the same anonymous browser may retry recovery (without checking the code again) or start setup directly before the original deadline. Recovery setup retains this challenge so failed Redis grant writes and lost setup responses can be retried; each setup attempt creates new pending credentials. A spent code cannot authorize another challenge and remains spent after abandonment or expiry. See [ADR-0023](./adr/0023-resumable-totp-recovery.md). Confirmation replaces the previous secret/recovery set and invalidates old sessions and grants. Employees have no recovery codes: an authenticated owner resets their 2FA with current password and an unused TOTP at POST /api/employees/{id}/totp/reset. This is a company-scoped protected write with CSRF and expected-session context. It revokes the employee's old sessions/grants and forces enrollment after password verification. No owner can reset an OWNER account. Password recovery and disable/re-enable never remove an enrolled TOTP credential.

There is no disabling or phone-transfer API. Use the authenticator's export/backup facilities where supported. For owner loss of both app and all recovery codes, follow the identity-verified [operator recovery procedure](./deployment.md#owner-totp-recovery).
